# Android performance audit — 5 November 2026

The project now targets 60 FPS on mobile and has a smaller CPU, allocation and rendering budget. Sustained 60 FPS on a particular Android phone has **not** been measured. Editor checks below verify behavior and configuration, not device frame time or thermal stability.

The gameplay source directory is `Assets/_Game/Scripts`, rather than `Assets/Scripts`. The audit scanned all project C# sources, including runtime builders and the Maeko flock implementation, plus all 27 ProjectSettings files. It inspected both URP pipeline assets, the Mobile renderer, and read scene data without editing scene YAML.

| Bottleneck found | Evidence and implemented change |
| --- | --- |
| Dense course construction and activation | The previous task's `TrackDistanceStreamer` already reduced the roughly 1,160-object course to a nearby subset. It remains the culling authority: `[Camera.main.z - 15, max(Player.z, Rival.z) + 110]`, checked at 10 Hz. Collected pickups cannot respawn. Ground, water, finish, characters, HUD, managers and bridge decks stay persistent. The 110 m forward margin preserves the earlier requested window and Rival interaction distance. |
| Repeated roadside creation/destruction during play | `TropicalScenery.Refresh` instantiated incoming chunks and destroyed outgoing chunks every 0.2 s. Chunks now return to queues per prefab and are reused before creating another instance. The streamer unregisters a chunk before reuse and registers its new Z, avoiding stale consumed/hidden state. |
| Frequent pickup particle allocations | `BananaPickup.PlayPickupEffect` and `PowerUpPickup.PlayCollectionEffect` instantiated and destroyed a particle hierarchy per collection. `PickupEffectPool` now reuses completed bursts, retains at most 12 idle instances per prefab, and checks completion at 10 Hz. Rival bursts remain silent; reuse restores the prefab's audio enable/mute state for player bursts. Pool objects belong to the scene. |
| Repeated AI hierarchy lookups | Rival banana scoring, hazard classification, bridge rejection, and bomb ground checks repeatedly queried components on the same physics colliders. `TrackColliderCache` caches classifications, including misses, until scene unload. Gorilla obstacle lookup uses the same cache. Existing nonallocating physics queries, decision cadence and jump/slide rules remain intact. |
| Duplicated magnet work | Every active banana evaluated both runners' magnet state and targets independently. `RunnerMagnetTargets` shares one snapshot per frame and still chooses the nearest eligible runner. Activation invalidates the snapshot. Magnet logic already used static player/rival references; it did not perform a scene search per banana. |
| HUD string churn | `LevelProgressHUD.Update` interpolated the same distance string every frame. It now calls TMP's numeric `SetText` only when displayed meters or total length change. `PowerUpManager.RefreshIndicator` rebuilt colored names, uppercase enum strings and formatted floats every frame while an ability was active. Prefixes are cached; countdown text rebuilds only when a displayed tenth changes and passes its reused StringBuilder directly to TMP. Inventory counters were already event driven. |
| Missing-reference searches | `BananaCounterUI.SyncQuota` retried `FindAnyObjectByType` every frame if the gate was absent. Resolution now occurs during startup. Power-up model fallback lookup is limited to once per second while unresolved; health and ability-visual components are cached. Streamer scene/camera resolution is conditional and limited by its 10 Hz refresh. |
| No explicit mobile 60 FPS policy | `MobilePerformanceBootstrap` applies `Application.targetFrameRate = 60` and `QualitySettings.vSyncCount = 0` on mobile. Desktop rendering settings remain unchanged unless the explicit Play Mode mobile-preview method is invoked. |
| Mobile GPU configuration | `Mobile_RPAsset` already used 0.8 render scale, one cascade, no MSAA, no soft-shadow support and no additional-light shadows. It still enabled HDR, 50 m URP shadows, and up to four per-pixel additional lights. A runtime pipeline clone now caps render scale at 0.8, disables HDR, caps shadows at 30 m/one cascade/1024 resolution, and limits additional lights to two. The lighting mode is retained. Camera post-processing is disabled on mobile; no global Volume was found in the inspected scenes, so bloom/DOF/motion blur were not demonstrated existing bottlenecks. |
| Shadow policy overridden each frame | `LevelEnvironmentManager.ApplyProgress` assigned `LightShadows.Soft` every frame. It now respects the mobile hard-shadow policy. Repetitive pickups, trees/foliage, particles and trails have shadow casting/receiving disabled under the mobile profile. Character and large-structure shadows are retained. |
| Material configuration and resource lookup | Runtime material factories now enable instancing; scene and streamed shared materials are also prepared once when registered/loaded. All gameplay `Resources.Load<T>` calls route through a typed dictionary cache, including failed lookups. The cache clears on scene unload, releasing menu asset references. |
| Native asset lifetime | The diorama was already scene owned, with no `DontDestroyOnLoad` on its hierarchy. However, its generated materials, textures and mesh lacked explicit destruction. `RuntimeAssetOwner` now releases these assets, plus generated ability materials/ring meshes and builder materials. Imported/shared assets are never owned or destroyed by this helper. |
| Repeated bridge geometry sampling at startup | Each of three identical bridge instances repeated 257 longitudinal and 257 lateral ray samples over its mesh colliders. The native prefab profile is now sampled once per prefab asset and fitted independently at each crossing. The walking ribbons, collision rules and curved deck geometry are preserved. |
| Quadratic flock steering | `MaekoFlock.UpdateBird` compares each bird with the flock. Level01 authored flocks contain 32 and 24 birds. Mobile initialization caps each flock at 16, reducing those neighbor-loop iterations from 1,600 to 512 per simulation tick, while preserving both animated flocks and desktop counts. |

The existing project already uses IL2CPP/ARM64, incremental GC, multithreaded rendering, nonallocating Rival physics queries and disabled automatic physics transform synchronization. These were retained. Fixed-step timing and physics solver settings were retained to protect movement and bridge behavior. No blanket scene-search replacement was applied to startup, screen-resize, collision-event or one-time cutscene setup paths.

Instancing flags do not guarantee fewer draw calls. Unity prioritizes the SRP Batcher for compatible URP renderers, and shader/mesh/material compatibility still matters. The SRP Batcher remains enabled as Unity recommends; visible-object reduction is the verified reduction in submitted scene work. See [Unity's instancing guidance](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/reduce-draw-calls/gpuinstancing/gpu-instancing-enable) and [URP performance guidance](https://docs.unity.cn/6000.1/Documentation/Manual/urp/configure-for-better-performance.html).

Validation performed in the Unity Editor with the mobile runtime profile:

- 42 runtime assertions passed across rendering/lifecycle/bridge/resource, pooling/HUD, and streamer checks. The final sampled run registered 1,148 track objects with 79 active; 1,068 checked small-prop renderers had shadows disabled. Counts vary with course randomization and camera position.
- The original 11 streamer regression assertions passed, including both runner orderings, exact boundaries, moving objects, consumed pickups, and persistent exclusions.
- Foliage allocation plateaued at 10 chunk children after warmup and remained at 10 after 24 chunk advances. Reused visible chunks reactivated correctly.
- Particle completion returned a burst to inactive storage; a later request reused that same instance and restored player audio after a silent Rival request.
- 120 repeated active-countdown HUD updates allocated zero managed bytes when the displayed tenths stayed unchanged. This measures that update path, not the whole game's frame allocation.
- All 14 recorded generated menu assets were absent after loading Level01; the diorama hierarchy was also absent.
- All three bridge profiles retained more than 100 height samples, endpoints met the banks, and registry height queries matched their profiles.
- The authored Mobile URP asset remained unchanged; mobile settings apply to a runtime clone. Scene YAML was not edited.
- `dotnet build BananaRun.sln -m:1 -p:Configuration=Debug -p:UseSharedCompilation=false --verbosity minimal` succeeded with 0 errors and 281 existing warnings. Unity compilation also passed, and the final Play Mode console reported zero errors.

The course is still constructed synchronously at scene entry, and culling does not unload distant meshes/textures. Pool warmup and first shader use can still produce startup work. Final acceptance requires a Development Build profiled on a representative low-range and mid-range Android device: check CPU/GPU frame times against 16.67 ms, GC allocations, render batches, memory and thermal behavior during a full 1,500 m race, repeated restarts, magnets, ability effects and all bridge crossings. This audit does not claim an Android FPS measurement.
